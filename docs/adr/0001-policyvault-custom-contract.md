# ADR-0001: 자체 PolicyVault 컨트랙트로 지출을 통제한다 (ERC-4337 스마트 계정 대신)

> 상태: 제안
> 날짜: 2026-09-28

## 맥락

- 에이전트가 쓰는 돈의 한도를 AI가 아니라 코드와 온체인 규칙이 판정해야 한다 (PRD 핵심 가치, F-03).
- 에이전트 주소는 규칙을 바꿀 수 없어야 하고, 사람(소유자)은 승인·중지를 브라우저 지갑 서명으로 한다 (F-02, F-04, F-05).
- 제출 마감 2026-09-30 12:00 KST, 1인 개발 (PRD N-01, OQ #1).
- 사용자가 이미 결정했다: "PolicyVault로 확정" (PRD 근거 표기 U-확정). ERC-4337 전체 구현은 PRD 범위 제외에 있다.

## 검토한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 자체 `PolicyVault` 컨트랙트 (토큰을 보관하고 `spend()`만 에이전트에 허용) | 규칙·사유 코드·이벤트를 직접 설계 → 차단 이벤트(ADR-0002)와 증거 해시를 원하는 형태로 남김. 번들러·페이마스터·EntryPoint 불필요. Hardhat 단위 테스트로 전 규칙 검증 가능 | 표준 계정 추상화 생태계와 호환되지 않음. 지갑 기능(임의 호출)은 없음 — 결제 토큰 이전만 가능 |
| B. ERC-4337 스마트 계정 + 정책 모듈(검증 로직을 `validateUserOp`에) | 표준 호환, 향후 세션 키·모듈 생태계 활용 | 번들러·EntryPoint·가스 후원 구성이 필요해 일정 위험 큼. 검증 단계에서 막히면 UserOp가 **체인에 올라가지 않아** "차단의 온체인 기록"(F-06)을 남기기 어려움 |
| C. 오프체인 정책 서버만 (컨트랙트는 단순 토큰 이전) | 구현이 가장 빠름 | 한도 판정이 운영자 서버에 있어 제3자가 기록만으로 재구성할 수 없음 — 챌린지 B "Approval & Evidence"와 핵심 가치에 어긋남 |

## 결정

A. 자체 `PolicyVault`. 결정적 이유: 차단을 포함한 모든 판정이 온체인 이벤트로 남아야 하는데, B는 검증 실패가 체인에 기록되지 않는 구조이고 C는 판정 주체가 운영자 서버다.

규격(역할 immutable, `spend`/`approve`/`reject`/`pause`/`unpause`/`setPolicy`, 이벤트·사유 코드)은 docs/Architecture.md "데이터 모델과 인터페이스 > 1. PolicyVault".

## 결과 (트레이드오프 포함)

- 얻는 것: 규칙 판정·차단 기록·증거 해시가 한 컨트랙트에 모여 제3자 재구성이 단순해진다. 로컬 Hardhat에서 전부 테스트 가능.
- 감수하는 것: ERC-4337 호환은 없다(PRD 범위 제외 — 향후 계획). vault 1개 = 소유자 1명·에이전트 1명·정책 1개로 고정되며, 역할 변경 함수가 없어 키를 바꾸려면 재배포해야 한다. 결제는 vault가 보관한 ERC20(MockKRWT) 이전으로 한정된다.
